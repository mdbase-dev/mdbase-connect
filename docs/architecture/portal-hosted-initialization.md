# Portal cloud-copy initialization

`POST /v1/account/collections` reserves the collection UUID against the signed-in account's original request ID. For a native cloud copy, after confirming the original genesis, it calls `POST /internal/v1/collections/initialize` on the hosted deployment. Only this creation path requests the new-collection layout; routine activation, existing published intents, migration, and mode transitions do not.

The call uses the existing control-plane-to-hosted service token and names the exact collection, original request ID, and time zone. It uses the same recorded log region as activation to place the actor on first contact. Escrow does not implement it. The hosted actor uses its current verified cloud-copy authority to submit one encrypted replica mutation. Both writes are create-only: `mdbase.yaml` is a resource with an absence precondition, and `_mdbase/README.md` is a record create at an exact path. A collision refuses the whole mutation. Neither the control plane nor the blind log stores the plaintext files.

The collection and request IDs derive a stable mutation ID. The hosted actor only confirms an applied log-derived receipt for that mutation; a pending or unknown append is not success. On replay the receipt is checked before capture, so an acknowledgement lost between the hosted append and the control plane's publication cannot overwrite later edits. A receipt whose applied outcome cannot be verified is not treated as confirmation. After publication, the control plane returns its existing creation result without calling the initializer again.
