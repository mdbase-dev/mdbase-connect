# Portal cloud-copy initialization

The hosted Worker exposes `POST /internal/v1/collections/initialize` separately from routine activation. The compatible Worker must be live before deploying the control-plane caller in each environment: Server CD deploys and verifies the control plane before it deploys the Workers.

`POST /v1/account/collections` calls the initializer only for a new native cloud copy. It reuses the collection UUID reserved against the signed-in account's original request ID, confirms the original genesis before calling the initializer, and publishes the creation result only after the Worker confirms. Routine activation, existing published intents, migration, and mode transitions do not request the new layout.

The call uses the existing control-plane-to-hosted service token and names the exact collection, original request ID, and time zone. It uses the same recorded log region as activation to place the actor on first contact. Escrow does not implement it. The hosted actor uses its current verified cloud-copy authority to submit one encrypted replica mutation. Both writes are create-only: `mdbase.yaml` is a resource with an absence precondition, and `_mdbase/README.md` is a record create at an exact path. A collision refuses the whole mutation. Neither the control plane nor the blind log stores the plaintext files.

The collection and request IDs derive a stable mutation ID. The hosted actor only confirms an applied log-derived receipt for that mutation; a pending or unknown append is not success. On replay the receipt is checked before capture, so an acknowledgement lost after the hosted append cannot overwrite later edits. A receipt whose applied outcome cannot be verified is not treated as confirmation. A published request returns its existing result without calling the initializer again.
