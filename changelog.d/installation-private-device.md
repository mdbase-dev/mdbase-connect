## Added

- An application can hold the key of an existing private collection on its own device, if the person allows it. It is off by default: an operator turns it on for a server with `MDBASE_NEXT_PRIVATE_APP_DEVICES=1`, which requires `MDBASE_NEXT_PRIVATE_BOOTSTRAP=1` and `MDBASE_CONNECT_AUTH_RATE_LIMIT_SECRET` (the server refuses to start otherwise). With it off nothing changes. An application whose registered manifest declares `offline.replica` may send `requested_private_device: true` whenever it starts sign-in or asks for more access; any other application, and any application on a server with the switch off, is signed in as before. Connect does not check who published an application, so the person's approval is the control. The sign-in page offers the person's private collections with a notice that the app on this device will hold their key, will be able to read them, and will ask for the encryption password, and that they should allow this only if they trust the app with that password. The person approves each collection and can revoke it the same way as a cloud copy. Revoking stops the server serving that device; it cannot take back a key the app already held. Approved collections come back in the receipt (`private_device_collection_ids`, or `added_private_device_collection_ids` after a later approval) and in `GET /v1/next/collections?include=mode`, where every row carries `mode`. For those collections only, the installation credential may enrol its device, refresh its log token, and read the account-key status and sealed bundle. See `docs/installation-private-device.md`.
