## Changed

- A search by name, path or a text field (`x.contains("…")` or `x.lower().contains("…")` on `file.path`, `file.name`, `file.basename`, `file.folder`, `file.ext` or a top-level frontmatter field) now parses only the records whose stored path or field can contain the text, instead of every record. Every row is still read and decoded once; the answer, its order, `has_more` and cursors are unchanged. This serves TaskNotes' record completion, Reader's find-by-URL and the `title.lower().contains(…)` search. Fields with a read default or a date-time declaration, nested fields and body text are evaluated as before.
- A projected (`select`) search of that form no longer lists an `expression_evaluation_error` diagnostic for each record the search cannot match (for example a record with no `title` when the search is `title.lower().contains("…")`): those records are no longer evaluated.
- On a host with a query budget (the hosted Worker, the browser and mobile apps), such a search is charged for the records that can match, not for every record in the collection. A selective search over a collection too large for the budget, which was refused with `query_budget_exceeded`, can now be answered. Rows the search rejects are read but not charged, as rows of another type or folder already were; a search that most records can match is still refused.
- While a type change is waiting to sync, a query that the index declines reads every record instead of the stored type and field entries, which describe the types as last synced. On a budgeted host this can refuse a query that was answered, possibly wrongly, before.
